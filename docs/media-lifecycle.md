# 媒体删除、恢复、清理与审计

面向部署管理员。界面上的用户操作说明见[记录、照片与相册](user-guide/records.md)。

## 状态

`Media.status` 有三个值：

- `ACTIVE`：正常显示，媒体接口可读取。
- `DELETED`：在回收站里，保留原图、缩略图、展示图、视频播放版和业务关联。
- `PURGING`：已被一次彻底删除认领，正在清理文件或数据库。此状态会阻止恢复，也不会被第二次清理任务重复认领。

记录（`Entry`）使用 `status = DELETED` 表示在回收站，并额外保存 `deletedFromStatus`，恢复时回到删除前的草稿/发布/归档状态。

## 软删除（界面上的“删除”）

删除照片时：

1. `Media.status` 改为 `DELETED`，记录 `deletedAt`，释放 `dedupeScope`。
2. **保留** `AlbumMedia`、`EntryMedia`、`TripVisitPhoto` 和 `MediaTag` 关联。照片只是从照片墙、相册列表、记录正文和旅行页面隐藏，关系没有被删除。
3. 对相册封面、记录封面、旅行封面、用户头像、家庭档案头像、物品照片这些“只能指向一张图”的字段：先把受影响的 ID 写成 `deletedRefs` JSON 快照，再清空字段，避免页面出现 404 图片。
4. 不删除任何文件。

恢复时按快照把封面/头像/物品照片写回；只在字段仍为空时写回，删除期间用户新选的封面或头像不会被覆盖。相册和记录还必须保留关联，否则说明用户已经主动移除。

删除记录时只把 `Entry.status` 改为 `DELETED` 并记录 `deletedFromStatus` / `deletedAt`；`EntryMedia`、`EntryProfile`、`EntryTag` 全部保留。照片文件不受影响。

删除相册只删除相册和 `AlbumMedia` 关联；`Media` 记录与文件保持原样。从相册移除照片只删除一条 `AlbumMedia`，不会把照片移入回收站。

上传页/编辑表单里的“移除”只是一次取消选择。如果这张照片已经被记录、相册、旅行、头像或物品引用（去重时会复用已有照片），服务端不会改变它的状态，避免用户从表单移除时误删正在使用的内容。只有从未保存过、没有任何关系的新上传才会在移除时清理文件和记录。

## 30 天保留

- 记录和照片统一保留 `30 × 24` 小时，按 UTC 计算；迁移使用数据库时间，运行时代码使用绝对毫秒。
- `deletedAt` 是唯一的保留期起点。恢复时服务端重新计算是否过期，不依赖界面显示。
- 超过 30 天的项目仍会在回收站显示（附带“已超过保留期，等待后台自动清理”），但不能恢复；用户可以提前彻底删除。
- 自动清理只由服务端 worker 执行，界面不会因为打开回收站而触发删除。

## 恢复

照片恢复必须同时满足：

1. `status = DELETED`（`PURGING` 会被拒绝）；
2. 未超过 30 天；
3. 原图仍在存储后端中。

恢复只更新状态，不新建 `Media`、不复制文件、不重新上传。相册关联、记录附件、旅行到访照片和标签天然保留；封面/头像/物品照片按快照写回。原始的 ID、上传者、拍摄时间、说明、收藏状态都不变。

记录恢复使用 `deletedFromStatus`，不会把草稿变成已发布。超过 30 天或状态已经变化时恢复失败，并提示刷新。

## 彻底删除与并发

只有 `DELETED` 状态可以认领彻底删除：

1. 用条件更新把 `DELETED → PURGING`，写入 `purgeStartedAt`。只有认领成功的任务继续。
2. 检查引用。会阻止删除的引用：
   - `EntryMedia`（记录正文/附件）
   - `TripVisitPhoto`（旅行到访）
   - 记录 / 相册 / 旅行封面
   - 用户头像、家庭档案头像
   - 物品照片
3. `AlbumMedia` 和 `MediaTag` 属于媒体自己的整理关系，**不阻止**删除；成功后在同一事务里移除相册关联、清空相册封面并删除标签。
4. 删除文件前再检查这些键是否被另一条 `Media` 记录共用；共用的对象跳过，不会因为一条记录清理而破坏另一条记录。
5. 文件按“缩略图/展示图/播放版 → 原图”的顺序删除；任一文件失败就回到 `DELETED`，写入 `purgeError` / `purgeAttemptedAt`，可以重试。
6. 全部文件删除成功、引用复查通过后，在一个事务里移除相册关联并删除 `Media` 行。

恢复和清理同时发生时，条件更新只有一个能成功：要么恢复成 `ACTIVE`，要么清理删除行；不会出现“恢复成功但原图已经没了”。两个清理任务同时运行也只有一个能认领，另一个直接返回。

如果 worker 在 `PURGING` 中途崩溃，15 分钟后下一次清理会把它放回 `DELETED` 并重新排队；文件删除是幂等的，重复执行不会误删其他媒体的对象。

## 自动清理

worker 每 10 分钟执行一次（启动后第一轮立即执行），即使当前没有待发提醒也会继续运行：

1. 回收超过 15 分钟仍停留在 `PURGING` 的认领。
2. 分批（每批 100，最多 4 批）永久删除超过 30 天的记录。逐条条件删除，一条失败不影响整批。
3. 分批永久删除超过 30 天的媒体。仍被记录/旅行/头像/物品/封面引用的媒体会保留并写入 `purgeError`；同一错误一小时内不重复重试，避免刷屏。
4. 每轮的清理数量、失败数量写入 worker 日志。

记录先于媒体清理：记录被删除后，它占用的 `EntryMedia` 会释放，照片可以在同一轮或下一轮被清理。

## 去重与上传者权限

图片去重范围是“上传者 + 可见性”（`Media.dedupeScope = <userId>:<HOUSEHOLD|PRIVATE>`）：

- 同一用户重复上传同一张图，复用自己已有的 `Media` 和文件。
- 不同用户上传同一张图，各自创建记录和文件。多占一份存储，换取“上传者始终能编辑/删除自己上传的内容”。
- 私有版本和共享版本不共用同一条记录。
- 视频、文档和历史数据不参与去重。

这取代了上一版“同一家庭共享图片共用一条 Media”的策略，因为那会让后上传的成员无法管理自己上传成功的照片。数据库唯一索引仍是 `[householdId, checksum, dedupeScope]`。

## 历史数据

- 旧版软删除已经物理删除了 `AlbumMedia`、封面、头像和物品照片字段。**这部分关系无法自动重建**。回收站会提示“这张照片是在旧版本中删除的”，恢复后照片能回到照片墙，但原相册/封面关系可能已经丢失。
- 旧版记录恢复逻辑不可用，且没有保存删除前状态；迁移后的历史记录恢复时统一回到 `PUBLISHED`。
- 迁移会给缺少 `deletedAt` 的历史回收站行**从升级时刻重新计算 30 天**，避免升级后立即批量永久删除。
- 旧去重范围会在迁移中改写为“上传者 + 可见性”，不删除、不合并任何媒体记录。

## 升级前的备份

1. 停止 web 和 worker（Docker：`docker compose stop`）。
2. 运行 `npm run backup`：`VACUUM INTO` 生成一致性数据库快照，并复制本地 `storage/`。
3. 把备份目录复制到另一块磁盘或另一台设备，确认 `homehi.db` 非空、`storage/` 文件数量合理。
4. 在测试环境用 `npm run restore -- <备份目录> --force` 演练恢复。
5. 升级后先运行 `npm run audit:media`，确认数据库与本地/OSS 对象一致，再启动 worker 让自动清理运行。

使用 OSS 时，`npm run backup` 只备份数据库；OSS 对象需要版本控制或跨区域复制。数据库备份中保留所有对象键，恢复数据库后要确保对应 OSS 对象仍然存在。

## 审计存储

```bash
npm run audit:media
```

脚本只读，不会删除或修改任何东西。它会：

- 汇总数据库里所有媒体记录的原图、缩略图、展示图和播放版键，以及议题附件；
- 按后端枚举实际对象（本地目录或 OSS 前缀）；
- 报告“数据库有记录但文件缺失”和“存储里有文件但数据库无引用”的孤儿；
- 检查数据库中出现过的后端，并额外检查当前活动后端和本地存储。

退出码为 `1` 表示发现问题，`0` 表示一致。输出最多展示每类 20 条样例。

注意事项：

- 上传或彻底删除正在进行时，原图可能已经写入但数据库行还没建好，审计会短暂报告孤儿。建议在低峰期或停止写入后运行，隔几分钟再跑一次确认。
- OSS 审计会列出配置前缀下的全部对象，对象很多时耗时和请求量随对象数增长；只读，不会产生写操作。
- 脚本不会自动清理孤儿。确认文件确实不再被任何数据引用后，再人工处理；不要用脚本直接批量删除 `storage/`。
